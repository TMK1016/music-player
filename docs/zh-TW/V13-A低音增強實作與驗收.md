# V13-A：低音增強實作與驗收

版本0.20.0／build30，2026-10-29。對應EQ-01／QA-01／PROFILE-01／QA-02。使用者已授權先採A方案並更新手機；[研究](V13低音增強研究與方案.md)保留當時尚未實作的歷史狀態。

## 這次處理什麼

七段EQ維持50／125／315／800／2k／5k／12.5kHz。低音是獨立的90Hz低架，保留原0～9dB數值與既有模式／綁定，不把七段EQ改回十段，也不改寫舊音效資料。

舊路徑一律根據濾波器最高增益降低全頻音量：全平並低音+6dB，前級約−9dB，使深低頻絕對電平接近低音0時，而人聲／中高頻下降。本版A用歌曲實際處理後的音訊決定補償，目標為減少這種不必要衰減，讓低音真正增加。

## 實際路徑

```text
播放：音檔 → 七段EQ（單一前級增益）→ 90Hz低架 → 既有殘響 → App音量 → 系統輸出
背景：同一完整音檔／相同取樣率 → Apple原生離線EQ／低架／殘響 → 響度及重建峰值估計
結果：通過最新歌曲／參數檢查 → 80ms分步套用前級補償
```

- `BassAnalysisService`為獨立actor，讀檔、解碼、離線渲染、統計及32筆記憶體快取皆在播放render callback與MainActor之外。每4096frames處理，定期檢查取消並讓出執行權；滑桿停止約300ms後才啟動分析。僅處理目前歌曲／參數，不掃描千首×全部模式。
- 快取鍵為本機URL、檔案大小、修改時間、七段EQ、低音、殘響與混合量；不保存私人音訊或輸出音檔，不做跨版本持久快取。曲庫匯入副本正常不改寫內容；檔案變更則重新量測。
- 參考路徑為相同七段EQ與殘響、低音0；候選路徑使用指定低音。兩路以Apple實際浮點音訊單元渲染、統一App音量1，避免把使用者音量旋鈕混進分析。分析含無殘響0.5秒尾端／有殘響20秒尾端，並非任意殘響長度的無限尾音保證。
- 響度使用K-weighting、400ms區塊／100ms步長、−70LUFS絕對門檻與−10LU相對門檻。小於400ms以可用能量估計，不稱完整標準節目量測；靜音不追增益。Accelerate向量化濾波與統計，避免逐樣本Swift陣列修改的分析成本。
- 峰值取左右最大值，使用Apple連續取樣率轉換：≤48kHz為4倍、≤96kHz為2倍、更高為原取樣；另保留0.5dB估計餘裕。這是工程上的重建峰值估計，不是認證true-peak meter或限制器。
- 計算參考增益 `gRef=min(原低音0的保守增益, -1.5-Pdry)`；最終單一前級 `g=min(0, Ldry+gRef-Lwet, -1.5-Pwet)`，下限−96dB。參考響度是相同EQ／殘響的bass-off版本，不是跨歌曲音量正規化。舊前級不再額外疊加於此結果。
- 尚未量測、量測失敗或不支援的取樣率，繼續使用原有保守餘裕；不憑短片段就宣稱已取得整曲峰值。新參數會取消舊分析與增益漸變，版本token防止舊歌曲／已關閉低音的結果晚到。音量旋鈕或相同設定不重啟分析。
- 介面僅補上「低音分析中…／音量已補償／已達峰值餘裕／使用安全餘裕」提示，保持原七段調音版面。補償結果於80ms內16步套用；不是宣稱所有參數變動都有完整sample-accurate ramp。

本輪沒有加入壓縮、限制器或諧波，也沒有改成逐喇叭DSP。峰值吃緊時仍可能需要衰減；數位輸出估計不保證藍牙編碼、車機、功放或喇叭完全無失真。之前的UI操作雜音問題仍需真機觀察，不以本輪低音量測宣稱全部消失。

## 測試與交付

模型／校正測試17組通過；Native驗證器直接渲染Apple路徑，非只比較設定值。初輪44.1／48／96kHz、低音+3／+6／+9共9組；+6設定40Hz提高約5.34dB，1kHz約−0.43dB，響度匹配在0.5LU目標內。另含極端EQ／低音疊加的峰值測試、取消與實際NativeAudioPlayer採用結果。最終版本重跑通過9組矩陣、AAC解碼、殘響尾音、強EQ重疊、稀疏低頻瞬態確實進入peakLimited分支、取消與舊結果不覆寫bass-off，以及音量／相同設定不重置補償。原130個EQ響應探測亦通過。

[實際渲染報告](../verification/V13-A-native-result.txt)／[9組數據CSV](../verification/V13-A-bass-plan.csv)。+6dB條件下三取樣率的40Hz增幅5.338～5.343dB，中頻變化−0.426dB，響度差<0.01LU。注意低頻是用相同參考增益的bass-off與實際補償後輸出相比；舊測試以相同headroom旁通作對照，只能證明低架本身有效，不能證明使用者的整體聆聽音量改善。

最終M2測試中8秒音訊分析約0.148～0.279秒；曾在其他編譯工作與背景節能影響下觀察顯著排程延遲，故不當成手機／長歌曲的等待時間承諾。驗證器以暫時process activity防止自身App Nap，測試後解除；未新增使用者系統設定。iOS／macOS Debug均BUILD SUCCEEDED。手機已由Xcode更新原安裝，顯示Running，PID1444，LibraryReady:tracks=1230。簽章產物Info.plist為0.20.0／30，背景audio宣告保留，production bundle不含changelog.json。沒有刪除App或曲庫；未替使用者啟動私人歌曲聽測。

朋友來源包 `deliverables/MusicPlayer-0.20.0-build30-Friend-Source.zip`：47個白名單檔案、35份目前Swift來源逐位元比對與ZIP完整性通過，不含本機簽章、憑證、帳號、私人媒體及快取。互動圖25節點、45筆日誌／111項變更及PM映射驗證通過。GitHub遠端同步須以實際推送核對為準，網路阻塞時保留本機提交及backups/local離線bundle；不宣稱已同步。

驗證器使用自製合成音訊，不打開私人曲庫、不向喇叭播放。數字為指定測試條件，不能推論所有商業歌曲低音必增同樣dB；尤其本身由低頻主導或峰值接近上限時，可恢復的增益較少。第一次完整分析有等待時間，期間仍走原路徑；完成後提示變成已補償，可再比較低音0／3／6。

## 維護

主要程式：`AudioLevelMeter.swift`、`BassAnalysis.swift`、`AudioPlayback.swift`、`PlayerModel.swift`。原`EQHeadroom.swift`估算器未改，是未分析時的fallback及bass-off參考，不應再把其低音+6的−9dB顯示誤稱為已分析結果。

測試來源：`BassPlanChecks.swift`、`NativeEQChecks.swift`、`AudioChecks.swift`。`python3 scripts/check_audio.py`跑模型並建原生驗證器；`--native-only`只重建原生驗證器，避免無關測試重跑。原生PCM需在NativeEQValidation.app執行取得結果，不以編譯完成冒稱渲染通過。

參考：原[W3C濾波公式](https://www.w3.org/TR/audio-eq-cookbook/)、[ITU-R BS.1770](https://www.itu.int/rec/R-REC-BS.1770-5-202311-I)與[Apple AVAudioConverter](https://developer.apple.com/documentation/avfaudio/avaudioconverter)。Apple內部濾波器及轉換器不假設等同外部估算係數，實際PCM另測。
