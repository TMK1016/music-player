# Music Player：需求與開發路徑

日期：2026-10-24｜規劃 v0.1｜產品名稱、播放平台與硬體架構均未凍結。

最新進度（2026-10-24，v0.2）：風格與色調已獲確認；已建立本機匯入、離線副本、播放與 Apple 原生 EQ，並完成基礎狀態／PCM 驗證。Rust DSP、完整音訊 QA 與實車驗收未完成，詳見[本機音訊實作與驗收](本機音訊實作與驗收.md)。以下仍是完整產品路徑，不代表全部節點完成。

## 1. 需求彙整

目標是車用離線音樂播放器，整合音樂匯入、歌單、細緻 EQ、可選音效與車輛設定，逐步擴大為有硬體條件限制的 DSP 系統。Mac 是已確認的開發環境；「iPhone 是主要播放端」只是依手機與車用情境提出的暫定建議。

| 類別 | 使用者需求 | 規劃方式 |
| --- | --- | --- |
| 音樂播放 | 本機、離線、歌單 | 本機先行，加入佇列、搜尋、播放進度與錯誤恢復 |
| 音源品質 | 好的音源 | 保留原始品質及來源資訊，不把有損檔轉無損宣稱成音質提升 |
| 調音 | 細緻 EQ、DSP 類功能 | 先做立體聲參數 EQ、前級衰減、限幅與旁通，再驗證多通道 |
| 音效 | 環繞及其他效果 | 可關閉的立體聲擴展／空間效果；實體環繞另需獨立通道 |
| 現有喇叭 | 前座高音與中低音分離、後座同軸 | 先調查被動／主動分音、擴大機與可存取通道 |
| 未來配置 | 不同車款、例如 16 顆喇叭 | 以通道路由、角色與硬體能力建模，不能只靠喇叭顆數套用參數 |
| 雲端 | iCloud | 第一階段解讀為 iCloud Drive 的自有音檔；不是 Apple Music 訂閱曲庫 |
| YouTube Music | 程式內取得歌曲、離線 | 保存原始需求；平台下載授權未成立前不列為可交付功能 |
| 簡化下載 | 下載後自動加入歌單 | 針對明確允許的來源建立下載→驗證→入庫→加歌單流程 |
| 開發與發佈 | Mac 開發、可下載、之後 App Store | 分開規劃 macOS 直接下載及 iOS 測試／商店發佈 |
| 工作方式 | 英文需求、繁體中文回覆、Rust 偏好 | 根目錄 TMK 準則與完整英文需求對照 |
| 可理解的管理方式 | 類似附圖的節點與任務 | 本輪提供互動流程圖與節點契約，後續串接真實事件 |

## 2. 三個先決條件

**A. 先確認實際播放裝置。** Mac 開發不等於成品必須在 Mac 播放。建議 iPhone 為車用播放端，Mac 作開發及 DSP 驗證；若使用者選擇先做 Mac 產品，則先交付 Mac 原生版本，手機與 CarPlay 改為後續獨立里程碑。若為 Android 車機，保留 Rust 核心，平台介面與發佈路徑需另行設計。

**B. 先確認訊號實際到哪裡。** 若手機只送 L/R 兩聲道給車機，播放器只能處理這兩條訊號；車機之後如何分配到前後座與其他喇叭由車機／外接 DSP 決定。即使車內有 16 顆喇叭，也不代表 App 可控制 16 路。應讀取有效路由通道數並實機送測試訊號驗證映射，不假設藍牙、USB 或 CarPlay 一定提供逐喇叭控制。[Apple 路由通道資訊](https://developer.apple.com/documentation/avfaudio/avaudiosession/outputnumberofchannels)

**C. 先確認音源能否下載、解碼與處理。** YouTube 一般開發政策限制下載、離線副本及分離影音。Premium 官方離線能力不等於本 App 可以讀取音檔或加上自訂 DSP。Apple 審核亦要求第三方下載取得來源明確授權。這是產品範圍限制，不是認定所有下載行為一概違法；內容權利與平台授權需要分開確認。[YouTube 政策](https://developers.google.com/youtube/terms/developer-policies)、[Apple 5.2.3](https://developer.apple.com/app-store/review/guidelines/#intellectual-property)

## 3. 車用 DSP 能做到什麼

| 模式 | 必要條件 | 可以提供 | 不能預先承諾 |
| --- | --- | --- | --- |
| 立體聲播放器模式 | App 能處理音檔並輸出 L/R | EQ、平衡、前級、限幅、可選立體聲音效 | 高音／中低音獨立分頻、前後座獨立延遲 |
| 多通道輸出模式 | 相容音訊介面、獨立擴大通道、接線及實測 | 每路 EQ、分頻、增益、極性、延遲與路由矩陣 | 任意車機或 CarPlay 都能存取全部喇叭 |
| 外接 DSP 控制模式 | 特定 DSP 有可使用的公開協定或 SDK | 透過協定設定硬體 DSP | 通用控制所有品牌或未知車廠封閉系統 |

前座分音喇叭若使用被動分音器，高音與中低音仍可能共用同一擴大輸出；App 無法在這條訊號之後把它們獨立調整。後座同軸也是相同原則。主動分音必須在擴大前對各單體分頻並有獨立路徑。[miniDSP 主動分音說明](https://support.minidsp.com/support/solutions/articles/47000681676-what-is-an-active-crossover-)

建議調音順序：確認接線與極性 → 量測與增益設定 → 若支援則分頻與時間對齊 → 適度 EQ → 等音量 A/B → 最後試聽音場效果。未知喇叭規格時不提供通用分頻點或大幅增益數字。車型與單體數只能當設定索引；真正的預設還應包含通道映射、座位、路由、量測版本及硬體識別。沒有校正量測與驗證，不能聲稱自動得到最佳設定。[miniDSP 車用調音](https://www.minidsp.com/applications/car-audio/3-car-audio-tuning-dsp)

立體聲擴展是可選效果，可能降低單聲道相容性或影響定位；它不等於實體多聲道、Dolby Atmos 或 DTS。後兩者涉及格式、硬體與授權，獨立評估，不列入首版承諾。這個 App 的 DSP 先限定於自己解碼播放的內容，不當作 iPhone 上其他 App 的系統級等化器。

## 4. 音樂來源與簡化流程

| 來源 | 第一階段能力 | 離線與 DSP 條件 |
| --- | --- | --- |
| 本機音檔 | 系統選檔、批次匯入、讀取標籤、歌單 | 能取得支援且未受 DRM 限制的檔案 |
| iCloud Drive | 系統檔案選擇器→等待雲端檔完整下載→複製至 App 管理區 | 需實際下載並標為保留離線；書籤或雲端占位檔不是離線副本 |
| 可授權下載來源 | 經核准來源連結／分享→下載佇列→驗證→入庫→歌單 | 來源條款與內容權利均允許；不依靠使用者勾選免責聲明取代授權 |
| YouTube／YouTube Music | 可先做來源連結收藏與導向官方 App | 收藏不是已下載歌曲；不假設公開 API 提供任意音樂音檔與 DSP 存取 |

目標操作流程：

```text
分享／貼上來源
  → 來源能力判定
      ├─ 允許取得原始音檔 → 下載 → 檔案與解碼驗證 → 原子入庫 → 加入指定歌單
      ├─ 本機／iCloud Drive → 選檔授權 → 複製與驗證 ────────────────┘
      └─ 僅允許外部播放 → 收藏連結／開啟官方 App（不顯示可離線）
```

實作須處理中斷、重試、取消、重複檔案、空間不足、來源失效，以及檔案成功但資料庫失敗的復原。歌單只引用已完成入庫的 track ID；連結收藏使用不同資料型別，避免顯示假歌曲。串流與雲端曲目只有完整下載且驗證後才標成「可離線」。

使用 `URLSession` 類原生機制處理下載；執行期不下載程式碼或以任意遠端腳本改功能。MVP 不預設需要伺服器。同步歌單與自有音檔是兩個需求：先完成手動 iCloud 匯入，再考慮 CloudKit 同步中繼資料、衝突解決與儲存成本。[Apple 檔案存取](https://developer.apple.com/documentation/uikit/providing-access-to-directories)

## 5. 建議技術架構與取捨

**建議 Rust 2024 edition＋Swift／SwiftUI＋AVAudioEngine。** Rust 處理 DSP、設定驗證與可重用領域邏輯；Swift 處理選檔、平台解碼、背景播放、Now Playing、遙控指令、路由變更及 CarPlay。這符合 Rust 優先偏好，同時減少自行重做 Apple 系統整合。[Rust edition](https://doc.rust-lang.org/book/appendix-05-editions.html)、[Apple Audio Engine](https://developer.apple.com/documentation/avfaudio/audio-engine)

| 方案 | 優點 | 成本與建議 |
| --- | --- | --- |
| Rust 核心＋Swift 原生殼 | 核心跨平台、DSP 可獨立測試、Apple 整合直接 | 有 FFI 與兩套建置成本；本專案優先驗證 |
| 全 Swift／原生音效單元 | Apple MVP 最快、系統整合較少橋接 | Rust 共用性較少；若跨語言驗證成本過高可提議改用 |
| Rust GUI／WebView 殼 | 適合重視跨桌面的 UI | 不會自動解決 iOS 背景播放與 CarPlay；若優先 Mac 跨平台再評估 |

預計結構（尚未建立／實作）：

```text
apps/ios/                 SwiftUI、背景播放、CarPlay
apps/macos/               可選的 Mac 播放與調音工具
crates/audio-dsp/         濾波、增益、延遲、限幅、旁通
crates/player-domain/     Track、Playlist、Profile 與設定驗證
crates/apple-bridge/      明確版本的 C ABI
tests/audio-fixtures/     自有／授權測試音檔及訊號
artifacts/                實測報告；預設不納入版控
```

先由 Apple 原生層解碼成 PCM；Rust 不必從首日承擔全部 codec。若需要跨平台解碼，再以真實音檔評估 Symphonia 的功能旗標、格式／codec 組合、gapless 限制與 MPL-2.0 授權，而不是把所有格式都列為已支援。首版格式候選：WAV、FLAC、MP3、AAC、ALAC；逐一通過平台與測試矩陣才列入正式支援。[Symphonia 官方支援表](https://github.com/pdeljanov/Symphonia/blob/main/symphonia/README.md)

資料儲存建議 SQLite 與有版本的 JSON 調音檔；是否使用 Rust SQLite 套件或 Swift 存取，在共用邏輯邊界驗證後決定，避免兩端同時直接寫資料庫。Track 記錄來源、原始格式、取樣率、聲道、檔案定位與離線狀態；Profile 記錄路由與通道角色，並在套用前驗證相容性。

## 6. 音訊管線與品質基準

```text
檔案／已完成的下載
 → 背景解碼與必要的取樣率轉換
 → 預先配置的 PCM 緩衝
 → 即時音訊回呼：Rust DSP
     前級衰減 → 參數 EQ → 可選空間效果 → 輸出限幅
 → Apple 音訊輸出 → 車機／擴大機 → 喇叭

條件式多通道分支：路由矩陣 → 每路分頻／EQ／延遲／增益 → 每路保護 → 獨立硬體輸出
```

這是建議管線；重取樣位置與效果順序在 spike 中用測試確認。全管線只保留一個回呼與輸出時鐘的擁有者，不混用兩個引擎搶硬體。使用固定大小緩衝與平滑參數更新；回呼內不做檔案 I/O、網路、阻塞鎖、記憶體配置或一般日誌。FFI 明訂 buffer 生命週期、frame／channel 排列與錯誤碼，不讓 panic 穿越 ABI。[Apple 即時回呼要求](https://developer.apple.com/documentation/avfaudio/avaudiosourcenode/init(format:renderblock:))

參數 EQ 建議先做可變頻率、增益、Q 值的 10 段架構，加上低／高架與高／低通的可擴充模型；這是產品建議，不是已實作數量。加入濾波器穩定性、有限數值檢查、平滑切換、保守增益、旁通與一鍵還原。多通道主動分音的保護需符合單體規格，不能只靠限幅器補救錯誤接線。

DSP 不會還原有損編碼已丟失的細節，藍牙或車機可能再編碼／重取樣；有 EQ 時也不應同時承諾 bit-perfect。紀錄原始格式與實際輸出格式，避免把高取樣率標籤當成音質證據。

驗收項目先定義方法，再依 GATE 結果訂硬數字：

- DSP 正確性：脈衝、正弦、掃頻、靜音、極值參數；測頻率響應、增益與穩定性，與參考公式／工具交叉比對。
- 即時性：記錄裝置、OS、路由、取樣率、buffer frames 與回呼 p95／p99／最大耗時；處理時間需留有低於 `frames / sample_rate` 的餘裕。256 frames／48 kHz 的單次時間是約 5.33 ms，僅為算例，並非端到端延遲承諾。
- 可靠性：規劃 60 分鐘真機連播、鎖屏、切歌與路由切換，記錄 underrun、崩潰、耗電與溫度；這些尚未執行。
- 音質：等音量旁通 A/B、單聲道相容性、削波與失真觀察；有量測設備後再建立座位響應與重現條件。
- 離線：先確認完整副本存在，再斷網、重啟、播歌；測磁碟不足及資料庫復原。不能以在線播放成功取代。

## 7. 開發路徑與可交付里程碑

完整節點契約、依賴與驗收見 `planning/flow.json` 及互動檢視器。以下是階段路徑，不是承諾工期。

| 階段 | 節點 | 交付物／進入下一階段的條件 |
| --- | --- | --- |
| 0 需求與能力 | GATE-01～03、ARCH-01 | 確認平台、接線、來源能力；記錄架構決策 |
| 1 垂直驗證 | SPIKE-01、CORE-01、QA-01 | 一個本機音檔經 Rust DSP 到真機，可旁通；有數值與回呼證據 |
| 2 離線播放器 | LIB-01、PLAY-01、EQ-01、PROFILE-01 | 本機音樂庫、歌單、播放控制、EQ 與相容預設；先完成這個 MVP |
| 3 雲端與取得 | CLOUD-01、SOURCE-01、DOWNLOAD-01 | iCloud Drive 保留離線；授權來源下載後自動入庫／加歌單 |
| 4 車內整合 | IOS-01、CAR-01、FX-01 | 背景、中斷、遙控與實車路由測試；CarPlay 經授權才交付 |
| 5 進階 DSP（選配） | MULTI-01、CAL-01 | 獨立通道、硬體映射及量測通過後，提供逐路處理；條件不成立則維持立體聲版 |
| 6 封測與發佈 | QA-02、FLOW-01、RELEASE-01、STORE-01 | 有可追蹤測試、可重現版本、授權材料與平台發佈包 |
| 獨立研究 | YT-01 | 取得符合需求的官方授權與技術能力前，保持「待授權」，不阻塞本機 MVP |

預估應在 SPIKE 完成後，根據可投入時數、支援裝置、格式與是否有外接 DSP 給區間；現在不提供看似精準的日期或成本。多通道與 CarPlay 不應變成本機 MVP 必須等待的前置。

## 8. Flow Inspector 與故障定位

本輪檢視器提供節點圖、點擊高亮前後依賴、節點任務、狀態、輸入／輸出、預計路徑與驗收。資料中的「等待確認／規劃中／條件式／待授權」都是規劃狀態，不是監控結果。完成這些規劃文件也不代表 GATE 已通過。

後續 FLOW-01 將規劃節點與實作契約連結：每筆測試或執行事件包含 `node_id`、版本、時間、run ID、嚴重程度、錯誤碼、路由與去識別化摘要；即時回呼只寫入預配置緩衝，由非即時執行緒輸出。測試失敗可自動連回節點，但原因可能在上游，不能將紅色節點直接等同根因。保留第一個錯誤、連動失敗與原始測試證據。

若發生問題，先重現→核對輸入與硬體能力→定位節點及依賴→提出修復→執行對應驗收→更新證據。節點內修復可繼續；若必須更動流程、音源能力或硬體要求，先提交具體差異供使用者討論。

## 9. 平台發佈與實車限制

macOS 可規劃 Developer ID 簽章、公證、乾淨機器安裝驗證，再提供 DMG／ZIP 下載；Mac App Store 另有 sandbox 與打包要求。iPhone 初期用 Xcode 真機測試，封測走 TestFlight，公開發佈走 App Store；其他地區／資格限定的替代分發不作預設。兩者不是同一套安裝包。[Apple Mac 發佈](https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases)

iOS 需設定音訊 session 與背景音訊能力，處理電話、Siri、導航 ducking、拔線、藍牙中斷及媒體服務重設。CarPlay 需要申請 entitlement 並使用允許的介面範本；其存在不代表取得車內 DSP 設定權。行車介面以選歌、播放與既有預設為主，細緻調音在停車時進行。[背景播放](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/playback)、[CarPlay entitlement](https://developer.apple.com/documentation/carplay/requesting-carplay-entitlements)

## 10. 下一步需要的資料
