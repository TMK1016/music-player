# 開發日誌與更新流程

2026-10-24｜v0.3.0。

依使用者要求，互動流程圖與 App 首頁側邊欄均加入「開發日誌」，共用 `planning/changelog.json`。目前回填初始規劃、v0.1 介面、v0.2 本機音訊與 v0.3 日誌功能四個階段。日期沿用實際工作日期，沒有捏造歷史發布時間。當時未接音訊的介面階段仍明確標示為歷史範圍。

## 點選後的位置

- 流程圖側邊欄：展開版本、點選改動 → 顯示改動內容與相關節點 → 選取並捲動定位節點 → 開啟實際程式或驗收文件。多節點改動可再點選其他相關節點。
- 每個節點的詳情新增「改動歷程」，可反查此節點在哪些版本被修改。
- 網址使用 `#node=...&release=...&change=...` 保留定位，重新整理／複製連結／瀏覽器返回後可還原。失效定位顯示提示，不選到不存在的節點。選取日誌時會清除舊搜尋，避免節點被搜尋效果遮蔽。
- App 側邊欄：點「開發日誌」，再點改動可展開節點 ID 與檔案位置；有產品介面對應的改動另提供「前往正在播放／音樂庫／等化器／車輛設定」。架構／驗收類改動顯示真實檔案位置，不假造不存在的功能頁。
- App 顯示的是可攜式相對檔案路徑，沒有假設其他裝置也能存取開發者的絕對路徑。流程圖的檔案連結需與專案檔案一起保留，瀏覽器可開啟檔案；不宣稱能在任何環境直接跳入 Xcode 某一行。

## 每次更新的交付步驟

1. 在 `planning/changelog.json` 最上方新增版本，或在尚未交付的同一版本補齊改動。每筆改動使用全域唯一且穩定的 ID，記錄內容、節點、真實檔案與可用的 App 功能頁。
2. 更新 `planning/flow.json` 的實作範圍、路徑、狀態及驗收證據。部分完成要保留未完成內容，不因新增日誌而宣稱功能已驗收。
3. 執行 `python3 scripts/generate_xcode_project.py`，同步 App 資源日誌；不直接修改 `apps/apple/Resources/changelog.json` 的產生副本。
4. 執行 `python3 planning/build_inspector.py` 重建離線流程圖，再執行 `python3 planning/validate_plan.py` 及其輸出的 JavaScript 語法檢查指令。
5. 檢查新改動的定位與功能跳轉；修改 App 時完成相應建置，再打包及交付。

驗證器會檢查：節點 ID／改動 ID 是否有效、相關檔案是否存在、路徑是否位於 Orca 工作區、App 目標頁是否有效，以及原始日誌、離線 HTML 和 App 資源副本是否一致。它不能自動判斷文字是否如實描述功能，因此每次交付仍須核對實作與證據。

這是人工維護的開發紀錄與定位功能；尚未實作 FLOW-01 原規劃中的自動測試事件、執行期監控或根因判斷。
