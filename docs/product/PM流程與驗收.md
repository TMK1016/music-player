# Music Player PM 流程與驗收

入口技能：[project-pm](../../../../Github/PM-skill/project-pm/SKILL.md)。採用 create-prd、prioritize-features、user-stories、test-scenarios 與 outcome-roadmap。讀取本機技能即可使用；不是安裝全域 plugin 或啟動 PM 服務。

需求原文保留於 notes/專案主筆記.md；產品基準為 PRD-music-player.md。planning/pm-plan.json 是優先序、故事、依賴及驗收的唯一 PM 任務來源；planning/flow.json 保留工程節點與證據，透過 node_ids 對應，避免兩份工程進度互相矛盾。互動流程圖提供 PM 階段、工作項及工程節點定位。

工作流：收集筆記／節點註解 → 明確交辦 → 對照PRD與範圍 → 更新任務／驗收 → 實作與測試 → 補證據 → 日誌與回饋。筆記保存或註解存在本身不授權執行。需求、拓撲、依賴變更須提出具體影響；此輪 PM 層疊加於既有25節點，不重排工程DAG。

## 成果路線

| 階段 | 使用者成果 | 出口 |
|---|---|---|
| Now | 本機歌曲可可靠離線聽，調音可保存與恢復 | PM-01～03 實測結果完整 |
| Next | 曲庫可整理，選曲與導覽可預期 | 先確認資料契約、評分邊界與介面稿，再依故事驗收 |
| Later | 雲端自有音檔與封測可控 | 下載交易完整、發佈檢查與測試範圍明確 |
| Conditional | 擴充前先辨識來源／硬體能力 | 各項取得前提與獨立決策，不阻塞本機MVP |

排序是工程建議，不是對筆記候選功能的開發授權。沒有團隊容量與實測工時，因此不編造 Sprint 日期。下一個可獨立進行工作為 PM-03 真機操作驗收；PM-01 的平台決策不阻塞這項測試。

共同角色：首位測試者；在停車或非駕駛狀態操作。每項執行後記錄裝置、版本、步驟、實際結果與證據，不能只勾完成。

|---|---|---|---|---|

## 風險與決策

首要風險是未完整驗收即擴充範圍，處理為先補 Now 證據；音效音量與實車感受不能靠文件證明。資料擴充須先定義版本遷移。統計／榜單沒有事件規則便不能先輸出假數字。正式平台與最低OS、未評分規則、有效播放門檻、導航稿為下一輪決策；產品與商店能力接近實作時再查官方最新資料。

本輪只導入 PM 管理架構與文件，不代表上述功能已開發。未做競品／市場研究、商業模式或固定工期估算。
