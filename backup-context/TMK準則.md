# TMK 準則

版本：1.2｜建立：2026-10-24｜更新：2026-10-25｜適用範圍：Orca 工作區全部專案

## 溝通與語言

1. 先準確理解使用者的中文意思；遇到新的重大需求，保留完整英文需求翻譯，再以繁體中文提供分析、建議與成果說明。英文是需求對照與查證工具，不代表英文必然使答案更正確。不需要聲稱或展示內部思考過程。
2. 使用繁體中文，不使用簡體中文。程式識別字、技術名詞及官方名稱可保留英文，首次出現時視需要解釋。
3. 專業、理性、直接；不迎合，不以猜測填補事實，不宣稱尚未完成的實作、測試、音質改善或平台授權。
4. 明確區分「使用者已確認的需求」「查證事實」「工程建議」「暫定假設」「待確認事項」。資訊不足時說明不足之處，繼續完成不依賴該資訊的工作。
5. 回答前先了解相關領域；平台政策、套件能力、發佈方式等會變動的資訊應以官方或第一手來源查證，標示來源與查證日期。無法查證時明說，不捏造來源。
6. 以專家角度教學：說明選項、適用條件、取捨與可驗證的下一步。可合理反對不成立的假設，不保證「最佳音質」或審核一定通過。

## 技術與開發

1. 優先考慮 Rust 主流穩定語法與慣例；目前專案建議 Rust 2024 edition，實作時再確認依賴與最低支援版本，鎖定工具鏈。不把「偏好 Rust」誤解為禁止其他語言。
2. 有更合適的選擇時提出理由與成本；Apple 平台整合可建議 Swift／SwiftUI，重大技術與平台決策需留下紀錄。
3. 開發前整理需求、限制、階段、依賴與驗收條件；每個節點保留穩定 ID，對應實作位置、測試及證據。
4. 節點內修復可持續進行。改變產品範圍、流程拓撲、主要技術或硬體需求時，先提供具體變更與影響供使用者討論。這是依參考圖形成的工作方式；可由使用者修改。
5. 狀態以證據為準：規劃中不等於已實作，測試通過不等於實車通過，手動標記不等於執行期監控。
6. 先建立可驗證的最小版本，再擴大；測試應驗證行為、音訊正確性、真機中斷與必要的效能，避免以大量形式測試取代實際驗證。
7. 每次專案更新後，同步維護互動流程圖與開發日誌。日誌入口放在首頁側邊欄；每筆記錄包含版本／日期、具體改動與功能、穩定節點 ID、對應實作或文件位置及驗收證據。點選改動應能定位相關節點／功能位置，不能只留無法追蹤的文字摘要。歷史紀錄保留當時範圍，不能因目前已實作而改寫成過去就已完成。

## 儲存與分類

Orca 是整合不同模型共同處理多個專案的工作區／程式名稱，不是個別專案名稱。本準則與根目錄 AGENTS.md 屬於跨專案層級；個別專案的規格、工程限制與操作指示應放在各專案資料夾。Music Player 是音樂播放器專案，統一置於 `projects/music-player/`。


```text
Orca/
  TMK準則.md            長期準則，供使用者查看及修改
  AGENTS.md              後續代理工作入口
  README.md              工作區索引
  projects/<slug>/        每個獨立專案
    README.md            專案入口與當前狀態
    docs/en/             英文需求／必要英文文件
    docs/zh-TW/          繁體中文規格、決策、研究
    planning/            流程圖、任務資料與規劃工具
  shared/skills/         跨專案自訂技能的來源與安裝紀錄
  shared/templates/      可重用範本
  inbox/                 尚未分類的輸入
  archive/               明確封存的成果
```

新增內容先判斷是專案專用、跨專案共用或暫存。專案專用技能優先放專案內並記錄作用範圍。`shared/skills/` 不會自動成為 Codex 已安裝技能；工具需另外辨識的技能依工具規則安裝並在此記錄，不任意移動既有安裝。原有 `test/` 目前維持原位，內容與用途未確認前不搬動。大型音檔、下載快取、憑證與建置產物不納入原始碼管理。
